## 1. TASK 한 줄 요약

[AI 설명] 결제 성공 시 결제와 같은 DB 트랜잭션에 Outbox 행을 남기고, 별도 폴링 작업이 그 행을 읽어 결제 건당 내부 알림 1건을 만들도록 했다.

## 2. 해결한 문제

[AI 설명]

- 기존 구조(ADR-003)는 결제 후속 처리를 결제 트랜잭션 안에서만 다뤘다. 결제 커밋 뒤의 후속 작업(알림)을 메모리 이벤트로만 넘기면, 커밋 직후 프로세스가 종료될 때 "이 결제에 알림을 만들어야 한다"는 처리 근거가 사라진다.
- 서버가 종료돼도 이미 커밋된 결제는 롤백되지 않는다. 유실될 수 있는 것은 메모리에만 있던 후속 처리 근거다.
- Outbox 행을 결제와 함께 커밋해 근거를 DB에 남기고, 재시작 후에도 남은 PENDING 행을 다시 처리할 수 있게 했다.
- 범위 밖: 알림 조회 API, 외부 발송, Kafka, 결제 실패·환불 이벤트의 Outbox, 다중 인스턴스 동시 폴링, 재시도 소진·최종 실패 상태(TASK-033-1).

## 3. 핵심 처리 흐름

[AI 설명] 사용자는 이 흐름을 단계별 보완 답변으로 확인했으나, 독립된 전체 설명은 [미확인]이다.

**결제 → Outbox (하나의 트랜잭션)**

1. `POST /payments` → `PaymentService.pay` (`@Transactional`)
2. 성공 시 `PaymentSucceededEvent` 발행
   - `@Order(0)` `PaymentStatusChangeListener`: 예약·HOLD·좌석 상태 전이 (TASK-032)
   - `@Order(1)` `PaymentOutboxListener` (`MANDATORY`): `outbox_event` INSERT (`PAYMENT_SUCCEEDED`, `PENDING`)
3. 커밋. 결제·상태 전이·Outbox가 함께 커밋되거나 함께 롤백된다
4. 커밋 성공 후 afterCommit에서 Redis 멱등성 성공 응답 저장

**Outbox → 알림 (폴링)**

1. `OutboxRelayScheduler` (`fixedDelay` 기본 5초)
2. `OutboxRelayService.relay()` (`NEVER` + `synchronized`): 잠금 없이 PENDING 후보 ID 조회 (순회 커서 뒤, 상한 이하, 최대 100건)
3. 후보마다 `OutboxItemProcessor.process(id)` (`REQUIRES_NEW`)
   - `SELECT … FOR UPDATE`로 행 잠금 → PENDING이 아니면 건너뜀
   - 알림 INSERT + `PROCESSED` 변경을 같은 트랜잭션으로 커밋
   - 예외 시 그 항목만 롤백되고 PENDING으로 남아 다음 순회에서 재시도

## 4. 기술 선택과 대안

[AI 설명] 사용자는 비용과 복구 장점을 보완 후 확인했다 (학습 방 보고).

| 선택 | 이유 | 대안과 차이 |
|---|---|---|
| DB Outbox + 폴링 | 결제 커밋과 알림 근거를 원자적으로 남김. 외부 브로커 미도입(ADR-001) | `AFTER_COMMIT` 리스너 즉시 처리: 커밋 후 종료 시 근거 유실 / CDC·Kafka: ADR-001과 불일치 |
| 항목별 `REQUIRES_NEW` | 한 건 실패가 다른 건을 롤백시키지 않음. 알림 INSERT와 `PROCESSED`의 원자성 | 배치 전체 1트랜잭션: 한 건 실패가 배치 전체 롤백 |
| 순회 상한·배치 제한 | 앞쪽 실패 건이 쌓여도 뒤 정상 건 진행, 새 행이 계속 추가돼도 앞 실패 건이 굶지 않음 | 단순 "오래된 PENDING N건" 조회: 앞쪽 실패가 batch를 채우면 정체 |
| 단일 인스턴스 + `synchronized` | 범위 단순화 | `SKIP LOCKED`, 분산 스케줄 잠금 (다중 인스턴스 필요 시) |
| 공용 스케줄러 풀 3 | 최소 변경, 자동 설정 유지 | relay 전용 스케줄러 bean: 기존 작업의 실행기까지 바뀜 |

## 5. 핵심 실패 상황

[AI 설명]

| 상황 | 동작 |
|---|---|
| Outbox 저장 후 결제 트랜잭션 장애 | 결제·상태 전이·Outbox 함께 롤백, Redis 성공 응답 미저장 (AC-2) |
| 결제 커밋 직후 프로세스 종료 | 커밋된 결제와 PENDING Outbox는 남는다. 재시작 후 새 순회가 처리 (AC-7) |
| 알림 INSERT 후 장애 | 알림과 `PROCESSED` 함께 롤백, PENDING 유지, 다음 시도에서 처리 (AC-6) |
| 같은 배치의 한 건 실패 | 그 건만 롤백, 나머지는 계속 처리 (AC-6B-1) |
| 같은 Outbox 재전달 | 잠금 후 상태 재확인으로 건너뜀, UNIQUE 제약이 최종 방어 (AC-5) |
| 알림 INSERT의 FK 검사 잠금 대기 | `payment`·`members` 행 공유 잠금을 기다리는 동안 relay 스레드가 멈춤. 풀이 1개였을 때는 HOLD 만료·대기열 작업까지 멈췄다 (Risk F-1) |
| 같은 건이 계속 실패 | 순회마다 재시도와 ERROR 로그 반복. 최종 실패 처리 없음 (현재 한계) |
| relay 전에 환불 | 결제 완료 알림이 그대로 생성됨. 결제 성공 당시 사실에 대한 알림으로 정의 (F-5) |

교정된 오해: "메모리 이벤트 방식이면 서버 종료로 이미 커밋된 결제도 롤백될 수 있다"는 오해를 설명으로 교정했다. 사용자 독립 답변으로 다시 확인하지는 못했다 (17번 항목).

## 6. 테스트가 보장하는 것

[AI 설명]

- 결제 커밋 시 PENDING Outbox 1건과 payload (AC-1)
- Outbox 저장 후 장애 시 결제·Outbox 함께 롤백 (AC-2), 결제 실패·거절·재요청에서 Outbox 미생성 (AC-3)
- 폴링으로 알림 1건 + `PROCESSED` (AC-4), 재전달·폴러 건너뜀에서 알림 1건 유지 (AC-5, AC-5S)
- 알림 INSERT 후 장애 시 롤백과 재시도 (AC-6), 배치 내 실패 격리·배치 너머 처리·앞 실패 재선택 (AC-6B-1~3)
- 다른 애플리케이션 컨텍스트가 남긴 PENDING을 새 컨텍스트가 처리 (AC-7)
- 스케줄러 자동 폴링, 빈 잔여 범위의 새 순회와 호출당 batch 상한 (후속 테스트 2개)
- relay가 결제 행 잠금에서 대기하는 동안 같은 스케줄러의 다른 작업이 진행 (F-1, 풀 1에서 Valid RED → 풀 3에서 GREEN)
- 로컬 전체 회귀 269/269, CI(`1ba4a80`) 269/269

사용자 확인 범위: 사용자는 학습 방 보고에서 테스트 결과를 Claude 보고와 GPT MASTER 검토를 통해 받아들였고, 실행 로그를 직접 확인하지 않았다고 답했다.

## 7. 테스트하지 못한 것

[AI 설명] 사용자는 순차/동시, 직접 호출/자동 실행, 대리 작업/실제 작업의 차이를 보완 후 확인했다 (학습 방 보고).

- 같은 Outbox ID의 `process` 동시 호출, `relay` 동시 호출. `FOR UPDATE`나 `synchronized`를 제거해도 현재 테스트가 통과한다 (Risk F-3)
- 실제 UNIQUE·FK 제약 위반과 깨진 payload 실패 경로 (현재는 flush 시점 주입 장애만, Risk F-4)
- 실제 HOLD 만료·대기열 작업과 relay의 병렬 실행 (F-1 테스트는 대리 카운터 작업)
- `members` 행 잠금 대기, `payment`·`members` 사이 교착 여부
- HTTP API로 시작하는 종단 흐름, dev profile 그대로의 스케줄러 등록 (Claude L-4)
- 다중 인스턴스, 장시간 실패 누적, 대량 PENDING 성능, CI 반복 실행 안정성

주요 발견:

- **F-1 (Medium)**: 스케줄러 스레드 1개를 HOLD 만료·대기열·relay가 공유해, relay가 FK 검사 잠금에서 대기하면 좌석 해제·대기열 입장도 멈춘다
- **F-2**: 알림 INSERT의 FK 검사가 `payment`·`members` 행에 공유 잠금을 요청한다
- **F-5**: relay 전에 환불돼도 결제 완료 알림이 생성된다
- **F-3·F-4**: 동시 실행과 실제 제약 위반 경로의 검증 테스트가 없다

## 10. 현재 한계

[AI 설명] (ADR-005 "현재 한계")

- 시도 횟수·마지막 오류·다음 시도 시각을 기록하지 않아, 계속 실패하는 건은 순회마다 재시도와 ERROR 로그를 반복한다
- 순회 위치가 메모리에만 있어 재시작이 잦으면 뒤쪽 건이 지연된다
- 처리 완료 행의 정리 정책이 없다
- 다중 인스턴스는 중복 알림만 막고 처리 분배는 하지 않는다 (미지원)
- 환불된 결제에도 결제 완료 알림이 남는다 (의도된 의미)
- 공유 테스트 DB에 기존 결제 회귀 테스트가 남기는 PENDING Outbox가 쌓인다
- 알림 처리 지연에는 폴링 대기(기본 fixedDelay 5초), 앞선 작업의 처리 시간과 순회 진행 시간이 영향을 준다. 잠금 대기·적체·반복 실패·재시작으로 더 지연될 수 있으며, 현재 보장하거나 검증한 최대 지연 상한은 없다
- 공용 풀 3은 스레드 대기만 분리한다. 잠금 대기 자체는 그대로이고, DB 연결 풀·Redis 경합 격리는 보장하지 않는다
