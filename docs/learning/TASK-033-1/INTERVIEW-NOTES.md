[AI 작성 설명 자료] 결제 성공 Outbox 처리가 실패하면 그 실패를 별도 트랜잭션에 기록하고, 정해진 대기 시간 뒤에만 다시 시도하며,

## 2. 해결한 문제

[AI 작성 설명 자료]

- **원래 동작 (TASK-033)**: 알림 생성이 실패하면 그 항목만 rollback하고 PENDING으로 남겼다. 실패 사실은 로그에만 있었고,
  다음 순회가 오면 조건 없이 다시 시도했다.
- 그래서 영구적으로 실패하는 건(이미 알림이 있어 UNIQUE 위반, 결제가 지워져 FK 위반, 깨진 payload)이 순회마다 같은 실패를 반복했다.
  몇 번 실패했는지, 왜 실패했는지 DB에서 알 수 없었고, 멈추거나 다시 넣는 방법도 없었다.
- 결제는 이미 커밋된 사실이라 알림을 버릴 수 없다. 대신 "언제 다시 시도할지", "언제 포기할지", "사람이 어떻게 다시 넣을지"를 정해야 했다.

## 3. 핵심 처리 흐름

[AI 작성 설명 자료]

```text
relay 호출 (T_poll)
→ 지금 대상인 PENDING 후보 [id, state_version] 조회 (다음 시도 시각이 없거나 지난 행)
→ 처리기: 행 잠금 (T_lock) → PENDING이고 지금 대상인지 다시 확인 → 알림 INSERT + PROCESSED (T_done)
   ├ 성공: PROCESSED, processed_at, next_attempt_at NULL, state_version +1, 실패 이력은 그대로
   └ 실패: 처리 트랜잭션 rollback
        → coordinator가 실패 감지 시각(T_fail)을 읽고 오류를 분류
        → 실패 기록기(별도 트랜잭션): 행 잠금 (T_rec) → PENDING이고 버전이 후보 조회 때와 같은가?
             ├ 예: 실패 수 +1, 마지막 실패 시각, 오류 분류, state_version +1
             │     실패 수 < 5 → next_attempt_at = ceil_s(max(T_fail, T_rec) + 대기)   ← 대기: 30·60·120·240초
             │     실패 수 = 5 → FAILED, next_attempt_at NULL (자동 순회에서 빠짐)
             └ 아니오: 아무것도 바꾸지 않음 (이미 처리됐거나 다른 회차)
→ 운영자: 원인 확인·해결 → CALL outbox_requeue_failed('[id, ...]', @n)
   → FAILED만 PENDING·실패 0·next NULL·state_version +1 → 다음 relay에서 즉시 대상
```

- **왜 실패 기록을 별도 트랜잭션에 남기나**: 처리 트랜잭션은 실패하면 rollback된다. 같은 트랜잭션에 실패를 기록하면 그 기록도 함께 지워진다.
  그래서 rollback이 끝난 뒤 새 트랜잭션에서 기록한다. 기록 자체가 실패해도 다른 항목 처리는 계속한다.
- **왜 잠금만으로 부족하고 버전도 필요하나**: 잠금은 "한 트랜잭션 안에서 확인하고 바꾸는 동안" 다른 쪽을 기다리게 한다.
  하지만 "처리 실패"와 "실패 기록" 사이에는 틈이 있다. 그 틈에 다른 경로(다른 JVM, 수동 재처리)가 행을 새 회차로 바꾸면,
  늦게 도착한 기록이 잠금을 얻은 뒤에도 새 회차 값을 덮어쓸 수 있다. 상태가 바뀔 때마다 올라가는 `state_version`을 후보 조회 때 값과 비교해,
  다르면 오래된 기록으로 보고 버린다.
- **왜 다음 시각을 초 단위로 올리나**: `next_attempt_at`은 초 단위 `DATETIME`이다. 10:00:00.500 + 30초 = 10:00:30.500을 버림으로 저장하면
  10:00:30이 되어 30초가 다 지나기 전에 다시 시도할 수 있다. 올림(10:00:31)하면 최소 대기보다 일찍 시도하지 않는다.
- **왜 폴링 시작 시각이 아니라 실패·기록 시각 기준인가**: 처리 중 잠금을 50초 기다린 뒤 실패하면, 폴링 시작 기준 "30초 뒤"는 이미 지나 있다.

|---|---|---|
| 지수 백오프 + 기록된 실패 5회에서 FAILED | 고정 간격 무한 재시도, 오류 종류별 즉시 FAILED | 일시 장애가 대기 사이에 회복될 여지를 두고, 기록된 실패가 설정 횟수(기본 5회)에 도달하면 자동 재시도를 중단한다. 그 도달 시간과 실제 시도 수의 상한은 보장하지 않는다. 오류 분류별 분기는 복잡도 때문에 넣지 않았다. 기본값은 측정 근거가 없는 설계 판단이다 |
| 별도 bean `REQUIRES_NEW` 실패 기록 | 같은 트랜잭션 기록 | 같은 트랜잭션이면 rollback에 기록이 지워진다 |

| DB 프로시저 수동 재처리 | HTTP 관리 API, 같은 jar의 운영 명령, SQL 스크립트 | 권한 체계가 없어 HTTP는 위험하고, 운영 명령은 다른 스케줄러까지 함께 돈다. SQL 스크립트는 입력 검증을 강제하지 못한다 |
| 허용 목록 오류 코드만 저장, 로그에서 예외 객체 제거 | 오류 메시지 저장, 정규식으로 민감 문자열 삭제 | 분류할 때 예외 메시지를 읽지 않으므로, 오류 분류 경로(새 오류 정보 컬럼)와 Outbox 자체 logger로는 메시지 내용이 옮겨지지 않는다. 다른 logger와 전체 출력은 이 보장 밖이다(§10). 기존 payload 컬럼은 이벤트 원문을 그대로 저장한다. 대신 로그에 스택 트레이스가 없어 진단이 어렵다 |
| Clock bean | `LocalDateTime.now()` 직접 호출 | 테스트에서 시각을 정확히 제어해 sleep 없이 경계를 검증한다 |

## 5. 핵심 실패 상황

[AI 작성 설명 자료]

- commit 시점 실패: 알림 INSERT 뒤 처리 완료 flush에서 실패 → 둘 다 rollback, 실패 기록
- 실제 DB 오류: UNIQUE(23000/1062)·FK(23000/1452) 위반, 깨진 payload → 그 항목만 rollback·기록, 같은 호출의 다음 항목은 처리
- 실패 기록 자체 실패: 그 항목은 횟수·버전이 그대로 남아 다음 순회에서 다시 대상, 다른 항목 기록은 계속
- 오래된 기록: 재처리로 새 회차가 된 뒤 이전 회차 기록이 도착 → 무시
- 다른 트랜잭션이 행을 잠근 경우: 기록기·프로시저가 기다린 뒤 최신 상태 기준으로 판단
- 재처리 도중 장애: 한 행을 바꾼 뒤 다음 행에서 실패해도 문장 전체가 반영되지 않음
- 재처리 입력 오류: 거부되며 아무것도 바뀌지 않음

## 10. 현재 한계

[AI 작성 설명 자료]

- 전역 logger `org.hibernate.orm.jdbc.bind`가 payload 바인딩 값을 출력한 것을 관찰한 뒤 공통 설정 기본값을 `"OFF"`로 바꿨다.
  확인은 격리 테스트 실행 범위이며, 운영 프로필·외부 설정의 실제 값은 확인하지 않았다. Outbox 자체 logger 비노출 테스트 통과는 전체 로그 비노출이 아니다.
- 실패 기록기가 엔티티 전체 UPDATE를 실행해 payload까지 다시 바인딩한다.
- backlog snapshot 조회 시점 (`OutboxRelayService.logBacklog()`): 마지막 출력 뒤 출력 간격이 지나지 않았으면 snapshot을 조회하지 않고 반환한다.
  간격 검사를 통과하면(아직 출력한 적이 없을 때 포함) relay 호출 끝에 snapshot을 조회한다. 결과가 비었거나 조회가 실패하면 마지막 출력 시각을 갱신하지 않으므로,
  다음 relay 호출에서 다시 조회할 수 있다. 조회 1회의 SQL 수는 대상 상태가 없으면 존재 조회 1개, 있으면 존재 조회와 기존 집계로 총 6개다(`OutboxBacklogQueryCostIntegrationTest`).
  실제 처리 시간과 대량 데이터 성능은 측정하지 않았다. 마지막 출력 시각은 로그 호출 직후 읽은 시각이며, 로깅 백엔드가 기록을 마친 시각과는 다르다.
- 프로시저 오류 경로 정리는 잠금 timeout(1205) 사례로만 확인했다.
- AC-10b probe는 강제 경로로 검증했고, 실제 `lock_data` NULL 상황의 probe 성공은 1회만 관찰했다(빈도·장기 안정성 미검증).
- 수정본 전체 회귀는 WORK-59 로컬 1회(383/383)이고 CI는 실행하지 않았다. WORK-47 381/381은 수정 전 소스 결과다. 다중 인스턴스·F-3 범위 밖.
- backlog 관측은 항목 처리 후 시각, 다음 간격 기준은 로그 호출 직후 시각이다. 로깅 백엔드의 최종 기록 시각까지는 검증하지 않았다.
- 실패 수는 실제 시도 수의 하한이다: 후보 조회 때 버전과 처리 회차가 다르면 기록이 무시되고, 기록 실패·중간 종료 때도 세지 않는다.
- 기본 대기 합 450초는 FAILED까지의 시간 상한이 아니며, backlog 건수·처리 지연의 운영 상한도 보장하지 않는다.
