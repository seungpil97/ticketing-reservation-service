# TASK 학습·이해도·면접 대비 계약

> 적용 대상: 티켓팅/좌석예약 백엔드 프로젝트의 각 TASK
> 목적: AI가 구현한 결과를 사용자가 자기 말로 설명하고, 기술 선택·실패 상황·테스트 한계·본인 기여까지 면접에서 방어할 수 있도록 검증한다.

---

## 1. 기본 원칙

1. 구현 완료만으로 TASK 학습이 끝난 것으로 보지 않는다.
2. 최종 코드와 리뷰 결과가 확정된 뒤 학습을 시작한다.
3. 설명을 읽는 것과 직접 설명할 수 있는 것을 구분한다.
4. 사용자가 답하기 전에는 모범 답안을 먼저 공개하지 않는다.
5. 틀린 부분과 빠진 부분만 보완한 뒤 같은 질문에 다시 답하게 한다.
6. 자료에서 확인된 사실, 합리적인 추론, 추가 확인이 필요한 내용을 구분한다.
7. 프로젝트 자료에 없는 내용을 사실처럼 만들지 않는다.
8. AI가 수행한 일과 사용자가 직접 판단한 일을 분리한다.
9. 치명적인 오개념이 남아 있으면 다음 단계로 넘어가지 않는다.
10. 최종적으로 30초·90초·심층 답변을 사용자가 직접 완성한다.

---

## 2. 적용 시점

대표·고위험 여부와 learning deadline은 TASK 계획 단계에서 승인한다.

- 계획에서 merge 전 learning gate가 승인된 TASK는 merge 전에 학습 검증을 통과해야 한다.
- 일반 TASK는 merge 후 학습을 진행할 수 있다.
- 모든 TASK는 TASK 최종 완료 전, 그리고 다음 핵심 구현 TASK 시작 전까지 필요한 학습 검증을 완료한다.
- commit·push·PR 이전 학습을 모든 TASK의 보편 필수 gate로 강제하지 않는다.

---

## 3. 학습용 입력 자료

새 GPT 학습 채팅에는 해당 TASK의 최종 자료를 하나의 학습 패킷으로 제공한다.

권장 파일명:

```text
TASK-XXX-LEARNING-PACKET.md
```

학습 패킷에는 가능한 범위에서 다음을 포함한다.

- Issue의 Goal, Background, Scope, Definition of Done, Test, Notes
- 변경 전·후 기준 SHA
- 최종 변경 파일과 핵심 diff
- 요청 처리 흐름에 필요한 주변 코드
- 실행한 테스트와 결과
- Claude Agent 리뷰 결과
- GPT 독립 리뷰 결과
- 최종 반영·미반영 Finding과 판단 근거
- 현재 구현의 확인된 한계
- 후속 TASK로 분리한 항목
- 사용자가 직접 결정한 내용
- 이 계약의 전문

독립 리뷰용 패킷과 학습용 패킷은 목적이 다르다.

```text
독립 리뷰 패킷
→ 다른 리뷰 결과와 예상 Finding을 숨기고 독립적으로 결함을 찾는다.

학습 패킷
→ 최종 코드, 두 리뷰, 최종 판단까지 제공해 전체 작업을 이해한다.
```

## 4. 1단계 — 작업 전체 설명

GPT는 먼저 다음 순서로 작업을 설명한다.

### 4.1 해결하려던 문제

- 어떤 비즈니스·기술 문제가 있었는가
- 이 문제를 방치하면 어떤 위험이 생기는가
- 티켓팅·예약·결제 도메인에서 왜 중요한가

### 4.2 최종 해결 구조

- 요청이 들어온 뒤 결과가 반환될 때까지의 전체 흐름
- 각 계층과 핵심 컴포넌트의 역할
- 상태가 어디에 저장되고 어떻게 변경되는가
- 트랜잭션과 외부 시스템의 경계

### 4.3 기술 선택 이유

- 왜 이 기술과 구조를 선택했는가
- 대안은 무엇이었는가
- 선택한 방식의 장점과 비용은 무엇인가
- 프로젝트 규모와 목표에 비해 과도하거나 부족하지 않은가

### 4.4 실패·운영 상황

- 동시 요청
- 중복 요청
- 재시도
- 롤백
- 외부 시스템 장애
- timeout
- null 또는 예상하지 못한 반환값
- 경계값
- 다중 인스턴스
- 로그·메트릭·알림
- 장애 복구와 데이터 정합성

### 4.5 테스트와 검증

- 각 테스트가 어떤 실패를 방지하는가
- 단위·통합·HTTP·동시성 테스트의 역할 차이
- 테스트가 실제로 보장하는 것
- 테스트가 보장하지 못하는 것
- 우연히 통과할 가능성 또는 거짓 양성
- 수동 검증에만 의존하는 구간

### 4.6 리뷰 결과

- Claude Agent와 GPT가 공통으로 발견한 문제
- 각 리뷰어가 단독으로 발견한 문제
- 심각도 판단이 달랐던 문제
- 최종 반영·미반영 결정과 그 이유
- 근거가 부족해 확정하지 못한 문제

### 4.7 현재 한계와 개선 방향

- 현재 구현의 한계
- 운영 전에 필요한 추가 검증
- 다음 TASK로 분리할 개선
- 다시 구현한다면 바꿀 부분
- 추가 복잡도를 감수할 가치가 있는 개선과 그렇지 않은 개선

## 5. 2단계 — 놓치기 쉬운 관점

GPT는 단순 요약에 그치지 않고 다음 관점에서 사용자가 놓쳤을 가능성이 있는 부분을 별도로 설명한다.

- 비즈니스 규칙과 코드의 불일치
- 상태 전이 우회
- 동시성 경쟁 조건
- 트랜잭션 경계
- 멱등성
- 재시도와 중복 처리
- 부분 실패
- 장애 전파
- fail-open과 fail-close
- 경계값과 시간 기준
- 서버 여러 대에서의 동작
- 관측성·로그·메트릭·알림
- 테스트 거짓 양성
- 테스트하지 않은 연결 구간
- 보안과 최소 권한
- 성능과 확장성
- 유지보수성과 문서 추적성
- 면접관이 후속 질문할 지점
- AI가 작성했지만 사용자가 직접 검증하지 않은 부분

각 항목은 다음으로 분류한다.

```text
확인된 사실
합리적인 추론
추가 확인 필요
현재 TASK 범위 밖
```

## 6. 3단계 — 이해도 확인

설명을 마친 뒤 GPT는 사용자의 이해도를 확인한다.

### 진행 규칙

1. 한 번에 질문 하나만 한다.
2. 사용자가 답하기 전에는 모범 답안을 공개하지 않는다.
3. 답변을 평가한 뒤 정확한 부분과 부족한 부분을 구분한다.
4. 부족한 개념만 짧게 다시 설명한다.
5. 같은 질문 또는 변형 질문에 다시 답하게 한다.
6. 통과한 뒤 다음 질문으로 넘어간다.
7. 사용자가 “모르겠다”고 답하면 정답만 주지 말고 단계별 힌트를 제공한다.
8. 사용자가 복사한 문장보다 자기 말로 설명하도록 유도한다.

### 필수 이해 질문

- 이 TASK는 어떤 문제를 해결했는가
- 요청 처리 흐름은 어떻게 되는가
- 핵심 기술은 어떤 원리로 동작하는가
- 왜 이 방식을 선택했는가
- 대안과 비교하면 어떤 장단점이 있는가
- 가장 위험한 실패 상황은 무엇인가
- 동시 요청이나 중복 요청에서 어떻게 동작하는가
- 테스트는 무엇을 보장하는가
- 테스트하지 못한 부분은 무엇인가
- 리뷰에서 무엇을 새로 발견했는가
- 현재 구현의 한계는 무엇인가
- 다음 개선점은 무엇인가
- 사용자가 직접 결정한 것은 무엇인가
- AI가 수행한 것은 무엇이며 어떻게 검증했는가

## 7. 답변 평가 기준

각 답변을 다음 기준으로 평가한다.

| 평가 항목 | 평가 내용 |
| --- | --- |
| 정확성 | 기술적으로 틀린 내용이 없는가 |
| 문제 이해 | 해결하려던 문제와 위험을 설명하는가 |
| 인과관계 | 문제, 선택, 결과가 논리적으로 연결되는가 |
| 동작 원리 | 코드 암기가 아니라 흐름과 원리를 설명하는가 |
| 선택 근거 | 해당 기술과 구조를 선택한 이유가 있는가 |
| 대안 비교 | 다른 방법과 장단점을 비교하는가 |
| 실패 대응 | 장애·동시성·중복·경계 상황을 설명하는가 |
| 테스트 이해 | 어떤 위험을 어떤 테스트가 검증하는지 설명하는가 |
| 한계 인식 | 현재 구현이 보장하지 못하는 것을 아는가 |
| 본인 기여 | AI의 수행과 본인의 판단·검증을 구분하는가 |
| 전달력 | 면접관이 이해할 수 있는 순서와 표현인가 |
| 과장 방지 | 검증하지 않은 내용을 구현 성과로 주장하지 않는가 |

평가는 다음 등급을 사용한다.

```text
통과
부분 통과
재학습 필요
근거 부족
```

## 8. 난이도별 목표 수준

### 일반 CRUD·문서 TASK

- 문제
- 처리 흐름
- 기술 선택 이유
- 기본 테스트
- 현재 한계

목표: Level 3 — 기술 선택을 설명할 수 있는 수준

### 인증·Redis·트랜잭션·동시성·결제·장애 TASK

- 정상 흐름
- 실패 흐름
- 동시성
- 정합성
- 테스트 한계
- 운영 관측성

목표: Level 4 — 실패 상황과 테스트 공백을 설명할 수 있는 수준

### 대표 포트폴리오 TASK 2~3개

- 대안 설계
- 트레이드오프
- 운영 확장
- 재설계 방향
- 측정 지표

목표: Level 5 — 기존 구현을 비판하고 개선 설계를 제안할 수 있는 수준

### AI 개발 프로세스·자동화 TASK

- 왜 자동화했는가
- 왜 완전 자동화하지 않았는가
- 권한을 어떻게 제한했는가
- 동일 입력과 독립 검토를 어떻게 보장했는가
- AI 결과를 어떤 근거로 채택·기각했는가
- 자동화 비용과 품질 개선 효과를 어떻게 측정할 것인가

목표: Level 4 이상

## 9. 면접 대비 단계

이해도 질문 통과 후 모의 면접을 진행한다.

### 9.1 기본 질문

- 무엇을 구현했나요
- 왜 필요했나요
- 본인이 맡은 부분은 무엇인가요
- 가장 어려웠던 점은 무엇인가요
- 어떤 테스트를 했나요

### 9.2 기술 심화 질문

- 왜 해당 기술을 선택했나요
- 대안은 무엇이었나요
- 동시 요청에서 안전한가요
- 장애가 발생하면 어떻게 되나요
- 현재 구조의 한계는 무엇인가요
- 운영 환경이라면 무엇을 추가하겠나요

### 9.3 압박·꼬리 질문

- 그 선택이 정말 최선이었나요
- 테스트가 통과했다고 안전하다고 볼 수 있나요
- 서버가 여러 대라면 어떻게 되나요
- 외부 시스템이 일부만 성공하면 어떻게 되나요
- AI가 작성했다면 본인이 실제로 한 일은 무엇인가요
- 같은 기능을 다시 만든다면 무엇을 바꾸겠나요

질문은 한 번에 하나씩 진행한다.

## 10. 최종 산출물

모든 TASK에서 최소 다음을 추적한다.

- pass 여부
- 핵심 오해
- 사용자 기여 / AI 기여 구분

대표·고위험 TASK는 다음 저장소 산출물을 필수로 작성한다.

```text
docs/learning/TASK-XXX/INTERVIEW-NOTES.md
```

일반 TASK의 `INTERVIEW-NOTES.md` 저장소 작성은 조건부이며, 필요 여부는 TASK 계획과 학습 중요도에 따라 판단한다.

`INTERVIEW-NOTES.md`를 작성하는 경우 다음 18개 항목을 내용 기준으로 유지한다.

1. TASK 한 줄 요약
2. 해결한 문제
3. 핵심 처리 흐름
4. 기술 선택과 대안
5. 핵심 실패 상황
6. 테스트가 보장하는 것
7. 테스트하지 못한 것
8. 리뷰에서 발견된 문제
9. 최종 반영·미반영 결정
10. 현재 한계
11. 다음 개선점
12. 사용자의 직접 판단과 기여
13. 30초 답변
14. 90초 답변
15. 심층 답변
16. 예상 꼬리 질문과 답변
17. 아직 약한 개념
18. 재복습 날짜 또는 조건

## 11. 통과 기준

다음을 모두 만족해야 학습 완료로 판정한다.

- 치명적인 오개념 0개
- 핵심 질문 통과율 80% 이상
- 문제 → 선택 → 구현 → 검증 → 한계를 연결해 설명 가능
- 코드 없이 요청 처리 흐름 설명 가능
- 최소 한 개 이상의 대안과 트레이드오프 설명 가능
- 핵심 실패 상황과 대응 설명 가능
- 테스트가 보장하는 것과 못 하는 것 구분 가능
- AI의 작업과 사용자의 판단·검증 구분 가능
- 30초 답변을 자료 없이 말할 수 있음
- 90초 답변을 자료 없이 말할 수 있음

미통과 항목은 `아직 약한 개념`에 남기고 다시 질문한다.

## 12. 새 GPT 학습 채팅 시작 프롬프트

아래 프롬프트와 `TASK-XXX-LEARNING-PACKET.md`를 함께 제공한다.

```text
첨부된 TASK 학습 패킷과 학습·면접 대비 계약만 근거로 진행해라.

목표는 결과를 요약하는 것이 아니라 내가 이 TASK를 자기 말로 설명하고,
기술 선택·대안·실패 상황·테스트 한계·본인 기여까지 면접에서
방어할 수 있게 만드는 것이다.

먼저 다음 순서로 작업 전체를 쉽게 설명해라.

1. 해결하려던 문제
2. 비즈니스·기술적 필요성
3. 요청 처리 흐름
4. 핵심 기술의 동작 원리
5. 기술 선택 이유와 대안
6. 동시성·장애·중복·재시도·경계 상황
7. 테스트가 보장하는 것과 보장하지 못하는 것
8. Claude Agent와 GPT 리뷰에서 발견된 문제
9. 최종 반영·미반영 판단
10. 현재 한계와 개선 방향
11. 내가 놓치기 쉬운 관점
12. 면접관이 물을 가능성이 높은 꼬리 질문

자료에서 확인된 사실, 합리적인 추론, 추가 확인이 필요한 내용을 구분해라.
자료 밖 내용을 사실처럼 추가하지 마라.

설명이 끝난 뒤에는 질문을 한 번에 하나씩 해라.
내가 답하기 전에는 모범 답안을 공개하지 마라.
내 답변의 정확성, 인과관계, 기술 선택 근거, 대안 비교,
실패 대응, 테스트 이해, 한계 인식, 본인 기여, 전달력을 평가해라.

틀린 부분과 빠진 부분만 설명한 뒤 같은 질문에 다시 답하게 해라.
치명적인 오개념이 없고 핵심 질문의 80% 이상을 통과할 때까지 진행해라.

마지막에는 내가 직접 작성한 30초 답변, 90초 답변,
심층 답변, 예상 꼬리 질문과 아직 약한 개념을 정리해라.
```

## 13. 금지 사항

- 자료에 없는 구현을 사실처럼 추가하지 않는다.
- 사용자가 답하기 전에 모범 답안을 먼저 공개하지 않는다.
- 한 번에 많은 질문을 던지지 않는다.
- 단순 암기를 이해로 판정하지 않는다.
- AI가 수행한 일을 전부 사용자의 직접 구현으로 표현하지 않는다.
- 테스트 통과만으로 운영 안전성을 단정하지 않는다.
- 이해하지 못한 항목을 자동으로 통과 처리하지 않는다.
- 면접 답변을 과장하거나 검증되지 않은 성과를 추가하지 않는다.

## 14. TASK 완료 정의와의 관계

이 계약은 기능 구현의 Definition of Done과 별개인 학습 완료 기준이다.

```text
기능 완료
→ 코드·테스트·문서가 승인된 범위를 충족

리뷰 완료
→ Claude Agent·GPT 검토와 Finding 판단 완료

학습 완료
→ 사용자가 문제·선택·원리·실패·테스트·한계를 자기 말로 설명

TASK 최종 완료
→ 기능·리뷰·필요한 학습 검증 결과가 모두 추적 가능
```

모든 TASK에서 동일한 깊이를 강제하지 않는다. TASK 위험도와 포트폴리오 중요도에 따라 학습 수준을 조정한다.
다만 모든 TASK는 TASK 최종 완료 전, 그리고 다음 핵심 구현 TASK 시작 전까지 필요한 학습 검증을 완료한다.
